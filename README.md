# K9R5-FPGA
IP and code for building K9R5 for an FPGA

K9R5 is a CVA6 + Ara vector processor on the [Cheshire](https://github.com/pulp-platform/cheshire)
SoC, with a [Spatz](https://github.com/pulp-platform/spatz) vector cluster to be attached as an
AXI accelerator.

## Layout

| Path | What | Pinned at |
|---|---|---|
| `cheshire/` | Base SoC | `mp/ara-pulp-v2` branch (the Cheshire + Ara integration) |
| `cva6/` | `pulp-platform/cva6` fork | `pulp-v2.0.0` (Ara and Cheshire's Ara branch pin `alpha.1`, whose `mstatus.FS` never turns Dirty on scalar FP writes; fixed in upstream commit `ecb138010`) |
| `ara/` | Ara vector unit | Ara `main` (bug fixes ahead of Cheshire's pin) |
| `spatz/` | Spatz cluster | in the dependency tree and generated (`hw/spatz/k9r5.spatz_cluster.hjson`); not yet instantiated in the SoC |

The repo root is a Bender package depending on Cheshire and Spatz. `Bender.local` overrides
Cheshire's `ara` and `cva6` pins with the local submodules, and pins packages shared with Spatz to
the newer of the two versions (Spatz pins older `axi`, `register_interface`, `riscv-dbg`, ...).
Neither tree resolves from scratch, so `Bender.lock` is generated by merging Cheshire's and Spatz's
locks; rerun `util/gen-bender-lock.py` after bumping `cheshire/` or `spatz/` (do not use
`bender update`).

Generated or patched sources never modify the submodules: they are written to `build/` and
swapped into Bender's generated source lists (`K9R5_SRC_SWAPS` in the `Makefile`). This covers
the Spatz cluster generated for K9R5 and Spatz's `spatz_vpu` sources with their `rvv_pkg` renamed
to `spatz_rvv_pkg` (Ara has a different package of the same name, and SystemVerilog packages
share one namespace).

## Setup

```bash
make k9r5-deps
docker build -t k9r5-fpga .
```

Run the container with the repo mounted **at the same path as on the host**: generated scripts
contain absolute paths.

```bash
docker run -it --rm -v "$PWD":"$PWD" -w "$PWD" -u "$(id -u):$(id -g)" -e HOME=/tmp \
  -v /tools/Xilinx:/tools/Xilinx k9r5-fpga
```

## Build (in the container)

```bash
make chs-hw-all                 # generate Cheshire's hardware (registers, peripherals)
make k9r5-spatz-gen             # generate the Spatz cluster (wrapper, bootrom, spatz_pkg) into build/hw
make chs-sw-all                 # Cheshire's own tests, e.g. cheshire/sw/tests/helloworld.spm.elf
make k9r5-sw-ara                # Ara's vector tests for Cheshire, into sw/build/ara/
make k9r5-xilinx                # VCU128 bitstream (K9R5_BOARD=vcu128 by default)
make k9r5-xilinx-program        # program the board over the Vivado hardware server
```

`ARA_CONFIGURATION` selects a file from `ara/config/` (default `2_lanes`, the only configuration
tested in Cheshire). Every Cheshire `chs-*` target is also available.

## Ara standalone testbench (in the container, Verilator)

Ara's own testbench (CVA6 + Ara with an ideal memory, no Cheshire) is the fast way to check vector
correctness and get cycle counts: Ara's `fmatmul` (32x32x32) runs in ~10 s.

```bash
make k9r5-ara-verilate                            # build the Verilator model (ARA_CONFIGURATION)
make k9r5-ara-app APP=fmatmul ARGS="32 32 32"     # build one of ara/apps (ARGS: problem size)
make k9r5-ara-sim APP=fmatmul                     # run it
make k9r5-ara-riscv-tests                         # all 228 riscv-tests in parallel, with timeouts
```

It uses Ara's pinned dependencies (CVA6 `alpha.1`) and Ara's pinned Verilator, which the image
installs in `ara/install/verilator`: with Verilator 5.050 (Spatz's pin) about 30 of the
riscv-tests hang. Ara's `crt0` enables the FPU itself, so the CVA6 `mstatus.FS` bug does not affect
these runs. Programs that use Cheshire's peripherals (`ara/cheshire/sw`, `k9r5-sw-ara`) need the
SoC simulation below.

## Simulate the SoC (in the container, Verilator)

The full K9R5 system (Cheshire with Ara and the Spatz cluster) runs in Verilator with the
testbench in `target/sim/verilator/`:

```bash
make k9r5-sim-build                                          # build the model (after HW changes)
make k9r5-sim BINARY=sw/build/ara/vector_helloworld.spm.elf  # run one program
```

`k9r5-sim` starts `BINARY` as Cheshire's testbench does in idle boot with serial link preload
(`BOOTMODE=0 PRELMODE=1`): it waits for the boot ROM to set up the LLC, preloads the ELF, writes
the entry point and launch signal to the `SCRATCH` registers and waits for the program's exit
code. Segments in DRAM are written straight into the testbench's memory; all others (e.g. the
SPM) go over the serial link. The run fails unless the program returns 0 (`[K9R5] SUCCESS`). Each
run stops after `K9R5_SIM_TIMEOUT` of simulated time (default `100ms`, `0` for no limit) and
prints the CPU's `pc`/`mcause`/`mepc`/`mtval`, so a program that traps fails instead of hanging.
The log is `target/sim/verilator/build/k9r5-sim.<binary>.log`, with the Spatz cores' instruction
traces in `target/sim/verilator/build/logs/`.

Building the model takes about 6 minutes on 12 cores. It simulates about 7 kHz of the 200 MHz
system clock with 4 threads, so `helloworld` (~440k cycles, dominated by the UART at 115200 baud)
takes about a minute, against more than 80 minutes for comparable programs in Questa Starter
Edition, which this flow replaces.

Options:

- `K9R5_VLT_THREADS`: model threads (default 4; 8 is ~10% faster, 2 ~25% slower).
- `K9R5_VLT_TRACE=1`: build a model with FST tracing (in `target/sim/verilator/build-trace/`), then
  pass `K9R5_VLT_TRACE=1 K9R5_SIM_TRACE=<file.fst>` to `k9r5-sim`.
- `K9R5_SIM_ARGS=+PROGRESS=<n>`: print hart 0's `pc` every `n` cycles.
- `K9R5_VLT_PATH`: another Verilator (Ara's pinned one by default); `K9R5_VLT_ARGS`: extra
  Verilator arguments.

The model is built with `-fno-dfg`: with Verilator's DFG optimizer, CVA6 hangs in the boot ROM.
`k9r5-sim` does not rebuild the model, so several runs can go in parallel.

Unlike Cheshire's QuestaSim testbench, there is no JTAG or UART preload, no autonomous boot (no I2C
EEPROM or SPI flash models) and no CVA6 instruction trace (CVA6 disables its tracer under
Verilator).
